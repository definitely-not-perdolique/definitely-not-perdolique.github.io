Рассмотрим поверхностно работу netfilter. Для начала что это вообще. netfiler - это модуль ядра который обрабатывает сетевой трафик. Грубо говоря фаервол. netfiler устроен как набор хуков, каждый из которых обрабатывает по своему пакет. Вот такие хуки:
PREROUTING - как очевидно из названия, переопределяет маршрут, т.е. перед тем как роутить можно что-то изменить.
INPUT - обработка тех пакетов которые идут на наш хост (dest наш ip например)
FORWARD - обработка пакетов которые идут на другой хост, но попали к нам. Т.е. на L2 уровне MAC наш, но IP dest другой.
OUTPUT - пакет с src нашим, т.е мы отправитель, это обработка исходящих пакетов
POSTROUTING - это уже после того как ядро linux решило кому отправить пакет - можно что-то сделать.

filter - отбрасывает или пропускает пакет
nat - выполняет nat
mangle - может изменять поля заголовка
raw - хз чё делает

--live - без остановки, тот самый итеративный процесс. Без флага будет пауза на всё время передачи памяти.

Продолжаем изучть мониторинг. Начнём с истоков. Вернёмся к QEMU. Наша виртуалка, с точки зрения хостовой ос - обычный процесс. Мы его можем убить при помощи kill. Но у нас есть возможность и управлять им. Но как? Мы же не можем просто так напрямую прочитать память процесса. Процесс же находится в ядре. Мы его тупо не видим, у нас разные адресные пространства. Чтобы его увидеть нам нужно применить IPC - межпроцесное взаимодействие, там shared memory итд которые все знают если изучали язык С. Так вот. В данном случае, для того чтобы почитать/записать какую-то инфу виртуалке используется сокет как вид IPC. Создадим новую vm'ку debian-11 и поищем его
`ps aux | grep qemu | grep 'debian-11' | grep 'monitor'`
Получим что-то типо
`-chardev socket,id=charmonitor,fd=37,server=on,wait=off -mon chardev=charmonitor,id=monitor,mode=control`
Это так называемый "монитор" - это и есть наш сокет. Он работает по протоколу QMP или HMP (qemu monitor protocol ничего необычного). Поищем теперь этот сокет
```
root@localhost:/vm/images# ss -xlp | grep debian-11
u_str LISTEN 0 1 /var/lib/libvirt/qemu/domain-3-debian-11/monitor.sock 105835 * 0 users:(("qemu-system-x86",pid=17852,fd=37))
```
вот он у нас. Теперь мы можем по нему "пообщаться" наверное!
`nc -U /var/lib/libvirt/qemu/domain-3-debian-11/monitor.sock`
НЕ МОЖЕМ. Ничего не происходит. Ну и ещё бы. Обратим внимание на ` Recv-Q Send-Q` в выводе ss. Там Send-Q = 1. То есть он принимает только одно соединение. Выполним ss -xlp ещё раз мы заметим как Recv-Q прибавился.
Дело в том что сейчас у нас уже подключен libvirt к этмоу процессу.
`ss -xp | grep monitor.sock`
Остановим libvirt
`systemctl stop libvirtd.service libvirtd.socket libvirtd-ro.socket libvirtd-admin.socket`
И подключимся
```
root@localhost:/vm/images# nc -U /var/lib/libvirt/qemu/domain-3-debian-11/monitor.sock
{"QMP": {"version": {"qemu": {"micro": 1, "minor": 2, "major": 10}, "package": "Debian 1:10.2.1+ds-1ubuntu3"}, "capabilities": ["oob"]}}
{"execute": "qmp_capabilities"}
{"return": {}}
{"execute": "query-status"}
{"return": {"status": "running", "running": true}}
{"execute":"query-name"}
{"return": {"name": "debian-11"}}
```
Опана! Работает. Мы только что отправили по голому протоколу L4 unix-socket данные, т.е. вручную пообщались по QMP. Запросили `{"execute":"query-name"}` - там выдало debian-11.
Собсна как вы понимаете, раз ранее подключен libvirt, мы подобные запросы можем писать через более привычный интерфейс
```
systemctl start libvirtd.service libvirtd.socket libvirtd-ro.socket libvirtd-admin.socket
virsh qemu-monitor-command debian-11 --hmp 'info status'
```
QEMU Monitor - это условно передняя панель физического сервера. Т.е. мы можем через него вырубить kvm, можем включить, проверить индикаторы, добавить диск, отключить диск, подключить ipmi. Вот за эту область отвечает монитор. Чего он делать не может - так это лезть внутрь ОС. Благодаря монитору мы можем собрать общую информацию о потреблении виртуальной машины, но мы ничего не можем знать о потреблении процессов внутри.
Для этого создадим отдельный сокет:
```
ps aux | grep debian-11 | grep socket
virt-xml debian-11 --add-device --channel unix,target.type=virtio,target.name=lab.test.0
virsh destroy debian-11 && virsh start debian-11
ps aux | grep debian-11 | grep socket
```
Обратим внимание как у нас запустился qemu. Channel в <devices> трансформируется в chardev по синаксису qemu. У нас добавился fd=30.
-chardev socket,id=charchannel1,fd=30,server=on,wait=off
-chardev socket,id=charmonitor,fd=37,server=on,wait=off
У нас создался канал через сокеты с хостом и вмкой. Проверим:
```
#на хосте
ss -xlp | grep debian-11
ls -lah /run/libvirt/qemu/channel/4-debian-11/lab.test.0

#на вмке
ls /dev/virtio-ports/lab.test.0
```
Вот такой вот крутая штука это channel. С одной стороны девайс-поток, с другой сокет. Мы даже можем по этому пайпу пошушукаться немного:
```
#на вмке (думаю очевидно что на вмке)
tail -f /dev/virtio-ports/lab.test.0

#на хосте
echo "privet iz hosta" | socat - UNIX-CONNECT:/run/libvirt/qemu/channel/4-debian-11/lab.test.0
```
Это и есть весь механизм. Никакой сети, никакой магии- байты через virtio.
Так вот, существует уже готовая служба `qemu-guest-agent` которая позволяет через этот сокет делать всякие вещи с вмкой находясь на хосте. Для начала с хоста выполним
` virsh domifaddr debian-11 --source agent`
Не открывается? ну очевидно потому что мы гуест-эйджент ещё не установили. Установим же
